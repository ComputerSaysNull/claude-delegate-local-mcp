## 2. Verdict

A careful, well-tested codebase with a strong safety culture: fail-closed defaults, server-
captured ground truth, a real path policy, and 1755 tests including 97 named regression
files. The main weaknesses are (a) two concrete process-boundary bugs around the stdio
transport and cancellation, (b) a few places where the sandbox's write access reaches files
the host later acts on, and (c) a documentation and comment load so heavy that it now hides
the logic and drifts — several model-facing texts are already stale.

## 3. Findings, most severe first

Severity is about consequence. IDs are stable so a later session can refer to them.

### R1 — High — `run_bash` inherits the server's stdin, which is the MCP stream (measured)

`sandbox.py` line 842: `subprocess.run(...)` passes no `stdin=`, so the sandboxed shell gets
the server's own fd 0. Under stdio that fd carries the client's JSON-RPC messages.

- Measured: calling `sandbox.run` with a marker line piped in, the sandboxed `read` printed
  the marker. With stdin closed it read nothing. A live delegation running
  `readlink /proc/self/fd/0` reported `pipe:[1312]`, which is the server's stdio pipe.
- Impact: any command that reads stdin (`cat` with no file, a REPL, a test that prompts)
  consumes protocol frames meant for the server, so requests are lost and calls hang until a
  timeout. It also gives a sandboxed command visibility into traffic that belongs to other
  delegations in the same process. The project guards stdout carefully
  (`docs/ARCHITECTURE.md`, "stdout belongs to the protocol"); stdin needs the same rule.
- Fix: `stdin=subprocess.DEVNULL` in `sandbox.run`, and the same for `paths._git`
  (`paths.py` line 427), `doctor.py` line 151 and `provision.py` line 312. `tools._run_git`
  already does this (`tools.py` line 989).
- Test (red first): run `sandbox.run` from a process whose stdin is a pipe holding a marker,
  and assert the command cannot read it. Negative control: the same test passes a marker
  through today.

### R2 — High — cancelling a delegation leaves its backend request running (measured)

`loop.py` lines 1144 to 1194, `_until_deadline`. The call is wrapped in
`asyncio.ensure_future` and awaited through `asyncio.wait`. If the *caller* is cancelled
(an MCP `notifications/cancelled`, a client disconnect), the `CancelledError` leaves
`asyncio.wait`, but the inner task is never cancelled. It keeps streaming to completion.

- Measured: a probe cancelled the caller 0.1s into a 1.0s inner call; the inner call was not
  cancelled and finished 1s later.
- This is very likely the root cause of **PLAN 59** ("a cancelled delegation keeps the
  cluster working"). The adapter's orphaned task keeps reading `aiter_lines()`, so the HTTP
  stream is never closed and vLLM never sees a disconnect. That matches the 281s of continued
  generation measured in #274. Meanwhile the admission lease is released, so the gate
  undercounts live load.
- Fix: in `_until_deadline`, on any exit other than normal completion (including
  `CancelledError`), cancel the task and await it. Closing the task closes the `httpx`
  stream, which is what makes the engine abort.
- Test (red first): the probe above, as a regression test, asserting the inner coroutine sees
  `CancelledError`. A second, integration-marked test can poll the endpoint's
  `num_requests_running` after a cancel.
- No existing test covers outer cancellation (searched `tests/` for `_until_deadline`).

### R3 — High — the read-write workdir reaches files the host acts on (read)

With a `workdir`, `run_bash` has a read-write bind of the project, which lives on `/mnt/c`
and is shared with Windows. The mount-level denylist exists to hide *secrets*. It does not
protect files that host-side tools treat as configuration or instructions: Claude Code's own
project settings and agent/skill files under `.claude/`, editor task files, `CLAUDE.md`,
and similar. Changes there take effect on the host, can take effect before anyone reviews a
diff (hooks apply mid-session, per this project's own memory), and a gitignored file does not
show up in `git status` at all. `write_file`/`edit_file` go through the path policy, which
refuses gitignored paths but not tracked configuration of that kind.

- This is a trust-boundary gap rather than a code bug. README says the project is "not a
  sandbox for untrusted code", but the threat that matters is untrusted *content* steering a
  trusted model, and that model has write tools.
- Fix direction (pick per file class): bind the host-configuration paths read-only inside the
  sandbox (the shadow mechanism already does this shape of thing), refuse them in the path
  policy for the write tools, and report any file the delegation created or changed that git
  ignores. Consider a small "protected paths" list beside `secret_globs.txt`, with the same
  single-reader rule.
- Test: a delegation-level test that a write to a protected path is refused by the file tools,
  and a `build_argv` test that such paths are bound read-only.

### R4 — Medium — host-side git runs where the model can shape repository config (read)

`read_git` (`tools.py` lines 1080 to 1174) and the gitignore layer (`paths.py` lines 437 to 529)
run the host's `git`, outside the sandbox, against any repository found under the workspace
roots. `run_bash` can create new directories, and a repository created during a delegation
is not covered by the point-in-time `.git/**` shadow. Git honours repository-local
configuration, so host-side git should not trust configuration it did not see before.

- Fix direction: pass hardening overrides on every host-side git call (for example disable
  fsmonitor, external diff and textconv, pager and hooks via `-c` settings, and
  `GIT_CONFIG_NOSYSTEM`), and/or refuse a repository whose `.git` appeared after the
  delegation started. `GIT_ENV_DENY` already covers the environment half.
- Test: a unit test asserting the argv carries the overrides, so a later edit cannot drop one.

### R5 — Medium — `provision` executes project-controlled build steps on the host (read)

`provision.py` lines 371 to 377 run `pip install --editable <project>` outside the sandbox,
with network and the full host environment (`build_env` removes only three pip variables).
The project's build backend and dependency declaration decide what runs, and a delegation
can edit those files. `--doctor` then reports the environment as stale, and the natural
response is to re-provision. Much of this is inherent to `pip install -e`, and the file
documents why it runs server-side, but the hand-off is not called out anywhere.

- Fix direction: before building, show the operator the diff of the dependency declaration
  since the last provision (the record already stores a hash; store the file too), or
  refuse to build from an uncommitted declaration. Longer term, run the build inside bwrap
  with network shared and nothing else of the host bound.
- Smaller defects in the same file (confirmed by reading):
  - `provision.py` lines 366 to 368 delete the working environment *before* the new build
    succeeds, so a failed re-provision (network down, bad pin) leaves no interpreter at all.
    Build into a temporary directory and rename.
  - `HASH_SOURCE` (line 66) is only `pyproject.toml`. A project declaring dependencies in
    `setup.cfg` or `setup.py` can change what gets installed without the hash moving.
  - A project with no `pyproject.toml` builds "successfully" but can never be current
    (`is_current` needs a non-null hash), so `$DELEGATE_PYTHON` is silently never offered.
    Refuse or warn at build time.
  - `run` catches only `ProvisionError` and `TimeoutExpired`; an `OSError` from `rmtree` or
    the record write surfaces as a traceback.

### R6 — Medium — server-format agent files are also loaded as Claude Code subagents (observed)

`.claude/agents/test-writer-local.md` and `docs-audit-local.md` are in this server's format
and live in the directory Claude Code reads its own subagents from. Claude Code loads them
too. This session's agent list shows both, as **"Tools: All tools"**, because they carry no
`tools:` key. A cloud session can therefore pick `test-writer-local` (its description invites
it: "Use after a bug fix...") and run a cloud subagent with every tool and a body written for
a different executor, which spends exactly the tokens the project exists to save.

- `agents.py` line 107 makes `.claude/agents/` the first tier, and the shipped skill
  `write-delegate-agent` tells users to put files there. So every adopter hits this.
- Fix: give server agents their own directory (for example `.claude/delegate-agents/` or
  `.delegate/agents/`), keep `.claude/agents/` as a read-only fallback for one release with a
  deprecation note in `list_agents`, and update the skill and `docs/AGENTS.md`.
- A related shadowing edge: `find_agent_file` returns the first file that exists, so a
  Claude Code-format file in the project tier makes a valid personal-tier agent of the same
  name unreachable (it fails validation instead of falling through).

### R7 — Medium — progress notifications are not monotonic (read)

`server.py` lines 769 to 779 report `progress(turn, of)` per turn, and the heartbeat paths
`ticked` and `alive` (lines 878 to 914) report `progress(0, 0)` repeatedly, including between
turns of an agentic run. The MCP specification requires the progress value to increase with
each notification. Claude Code only uses it to reset its idle timer, so it works here, but a
stricter client may drop or reject the stream. `total=0` also reads as "zero of zero".

- Fix: keep one monotonically increasing counter per call (turns and heartbeats both bump
  it), omit `total` where it is unknown, and put the human text ("turn 3 of 25", "queued
  41s") in the notification's `message` field.

### R9 — Medium — the turn-limit banner fires on a run that finished (observed)

A two-turn probe (one tool call, then the answer) came back with the banner "the delegation
ran out of turns while still working ... a report of an unfinished investigation". It had
finished. `hit_turn_limit` is `turn == turns` by design (`loop.py` line 3284, docstring at

### R18 — Medium — cancelling a burst's opener fails every sibling that joined it (measured)

`admission.py` lines 583 to 589 and 611 to 615. When the delegation that opened the burst
wait is cancelled, `_settle_waiters(exc=CancelledError)` stores that `CancelledError` in the
shared future. Each joiner awaits it through `asyncio.shield` and lands in its own
`except asyncio.CancelledError` branch, so it gives back its (valid) slot and re-raises. The
comment beside the `except Exception` branch says "its siblings are not implicated", but
`CancelledError` is not an `Exception`.

- Measured: a joiner task that was never cancelled took the `CancelledError` branch.
- Impact: in a six-wide fan-out from one session (one server process), cancelling the first
  call during the idle-hold window fails the others that joined its wait.
- Fix: when the opener fails for any reason, settle joiners with their own snapshot (or a
  plain result) rather than the opener's exception; keep the `CancelledError` branch only for
  the joiner's *own* cancellation (`asyncio.current_task().cancelling()` tells them apart on
  3.11+).
- Found by the delegated pass on `admission.py`; checked by the experiment above.

### R19 — Medium — two concurrent openers can orphan a burst wait (read)

`admission.py` lines 583 to 598. `self._holding` is read at line 583 and written at line 598,
and when the local snapshot is not idle there is an `await` in between
(`_burst_open_elsewhere`, line 595). Two requests in one process can both read `None`, both
await, and both open a wait; the second overwrites the first future. Anyone who joined the
first future is never settled (`_settle_waiters` settles whatever `_holding` is at the time,
line 678) and waits with its slot held, with no timeout, until its client cancels. Needs
another process to be counting a burst at the same moment (for example `run` beside the MCP
server).

- Fix: re-read `self._holding` after the await and join it if someone opened one meanwhile;
  or keep the future in a local and settle *that* one rather than the attribute.
- Found by the delegated pass; the interleaving checks out against the code.

### R20 — Low — the one admit call that does not degrade (read)

`admission.py` lines 394 to 402 call `self._slots.admit(...)` with no `SlotsUnavailable`
handler, while `_drop_ticket`, `_burst_open_elsewhere`, `_announce_burst` and `release`
all degrade gracefully. A lock held past its 5s timeout fails the delegation instead of
falling back to per-process counting as the module promises.

Also from that pass, judged minor: `_write` truncates then writes, so a process killed

can suspend, so no cancellation can land there.

### R21 — High — `read_git` returns file contents the path policy would refuse (observed)

Observed by the operator: a running delegation was refused `security/secret_globs.txt` by
`read_file` (layer 3) and read it through `read_git` instead. The code confirms the route is
general. `_checked_args` passes every non-flag token through as a revision (`tools.py`
lines 1010 to 1046), and `_checked_paths` checks only that a path is relative and does not
climb (lines 1049 to 1077). None of layers 2 to 4 is applied. So `show` with a
`<revision>:<path>` token, `diff`, and `blame` return the contents of denylisted, gitignored
or non-allowlisted tracked files, and of anything in history. `ls-files --stage` lists blob
ids, and `show` accepts a blob id.

- Why it matters: layer 3's promise is "delegated models never receive credential material",
  and `.git/**` is denylisted in the sandbox precisely because history holds more than the
  worktree (`tools.py` docstring of `_read_git`). This repository's own history is protected
  by the secrets gate and gitleaks, but the other workspace roots have no such gate, and a
  key committed and later deleted there is reachable.
- Fix direction: for content-producing subcommands (`show`, `diff`, `blame`), require every
  revision token to resolve to a commit (refuse blobs, trees and `rev:path`); add exclude
  pathspecs generated from the denylist and the extension allowlist; refuse `blame` and a
  `paths` entry that fails layers 2 and 3; and run the existing key-material marker check
  over the output as a last net. `secret_globs.txt` itself is harmless, so the observed case
  is a good regression fixture.
- Test (red first): `read_git show HEAD:security/secret_globs.txt` must be refused; so must a
  blob id taken from `ls-files --stage`.

### R22 — Low/Medium — the split-dodge check cannot fire in CI (read; from a delegated pass, checked)

`scripts/docs_gate.py` line 1469: `check_split_dodge` finds added documents with
`git diff --cached --name-only --diff-filter=A`, whatever the mode. A CI checkout stages
nothing, so in the one run `--no-verify` cannot skip (ci.yml's own header says that is what
CI is for) the check always sees no added files and passes. It only works in the optional
pre-commit hook. Fix: in `ci` mode, use the same `--diff` range the other checks use
(`git diff --name-only --diff-filter=A <range>`). Negative control: a branch adding a
document whose audience and owned code are a subset of an existing one must fail in `--mode ci`.

### R23 — Low — the gate's `run()` turns a failed git command into an empty answer (read)

`scripts/docs_gate.py` lines 123 to 126 return `stdout or ""` and ignore the exit code, so a
failing `git ls-files` or `git diff` reads as "no files", and checks built on it
(`check_secret_paths`, `check_never_tracked`, `scannable_files`) pass having looked at
nothing. The docstring calls a missing stdout "a real case rather than an error", which is
true for some callers and is exactly the fail-open shape this repository treats as its worst
kind of check. Fix: a `run(..., required=True)` variant that raises on a non-zero exit, used
by every check whose empty result means "clean".

Also from that pass, unverified: `check_roadmap_budget` does not reset its "live" state at a
section heading, so the first unmarked note under a new heading inherits the previous
section's last item (lines 1175 to 1176).

### R24 — Low — the "priced for" label is frozen at admission, and the real cap is not recorded (observed)

Spotted by the operator in the viewer, confirmed from the stream of the `docs_gate` pass:
all nine `priced` events say `expected_concurrency: 2, requests_running: 2.0`, although the
pass ran alone from about turn 3 (its own rate rose from 22.7 to about 40 tok/s, the solo
rate). The *pricing* did adapt, because from turn 2 the rate is the delegation's own
(`rate_source: own_turns`, 25.9 rising to 39.7). What is stale is the label, which
`run_delegation` computes once from the lease (`server.py` lines 948 to 950) and the loop
repeats on every turn.

- Two display problems follow. The viewer says "priced for 2" for the whole run; and the
  "budget" it shows is `budget_ceiling`, the time-derived bound (4 h of `dispatch_timeout` ×
  rate × 0.6 ≈ 240k here), which never binds early in a run. The value actually sent as
  `max_tokens` (the lower of that ceiling and the resolved per-effort budget) is not in the
  `priced` event at all, so a reader cannot see the real cap.
- One behavioural consequence, only with `rate_sample_seconds` set to 0: completed turns are
  then filed into the rate memory under the stale label (`loop.py` lines 3213 to 3221), so a
  run that went solo pollutes the two-wide bucket with solo rates. With the sampler on (the
  default) this does not happen.
- **Decided by the operator:** the viewer's budget shows `min(max_tokens, time-based
  budget)`, which is the value actually sent, so the `priced` event must carry it; and the
  concurrency is **re-read at every turn's pricing**. Read it from the shared slot totals
  rather than this process's own counters, so a sibling in another server process counts.
  Re-reading changes the label and what a sampler-off run files into the rate memory; it
  does not change the rate used after turn 1, which is the delegation's own.

### R25 — High — the model never sees its earlier reasoning, and `resend_reasoning` is inert (measured)

*Raised from Medium after the operator's review: it costs quality and cluster time on every
multi-turn delegation, and the worst case measured (the `docs_gate` pass) spent about 138k
tokens reasoning across its tool turns, each turn's thinking discarded before the next.*

**Fix path, in order — each step is cheap to measure before the next is built:**

1. **Find out what the model expects (spike, no code).** Read the served model's card and
   chat template for how it handles reasoning across tool calls. Some recent reasoning models
   are trained to keep their reasoning *within* one user turn while they call tools and drop
   it only at the next user message. If this one is, the stack is stripping something the
   model was trained to have, and the right fix is in the serving template (or a template
   argument vLLM passes through), not in this server. Also check whether the countdown
   `user` message the loop appends after every tool round would reset that window: if so,
   carry the countdown inside the tool result instead, where it would not count as a new
   user turn.
2. **Working notes in visible text (small code, A/B).** One static sentence in
   `SYSTEM_PROMPT_AGENTIC` asking the model, when it calls tools, to write a sentence or two
   first: what it has established, and what this call is meant to find out. Visible text
   survives in history, the prefix stays static, and it costs tens of tokens per turn.
3. **If notes are not enough: carry the tail of the reasoning as visible text (medium code,
   A/B).** The server already holds each turn's reasoning. It could append the last part of
   it (where conclusions usually sit, a few hundred tokens) to the assistant message as
   labelled visible text. History is append-only, so the prefix cache still holds. Costs
   prefill, which runs about 30 times faster than decode here, and needs the retention

Every turn, the model gets the task, the files, its own tool calls and their results, and

- Consequences: (1) `resend_reasoning` does nothing on this deployment, and its description

## 4. Cross-cutting: maintainability and documentation

Not bugs, but the biggest long-term risk in the project.

**The prose now outweighs the code.** Counted with the tokenizer: in `src/`, 9,114 code
lines against 6,563 comment and docstring lines (42% prose); `loop.py` has more prose than
code (1,619 against 1,465). 54 comment lines in `src/` carry a date. Much of it is history
("this said X until 2026-09-05", "measured on ..."), which is what CHANGELOG, JOURNAL and the
ADRs are for. The project already applies this rule to agent files ("state the rule, not the
incident"). The same rule for code comments and product-plane docs would cut a large share
of the text without losing any *why*, because the why is already in the ADR a comment can
link to.

**What the prose is, measured (added later).** A marker count (dates, "used to", "until",
"measured", "upstream") flags 8% of prose paragraphs as history, which is a lower bound. A
hand classification of 40 random paragraphs of three or more lines (seed 7, 1,012 in total):

| Kind | Share | Example |
|---|---|---|
| Design rationale worth keeping | ~60% (24) | why `"wb"` never sets `O_TRUNC`; why an agent name is checked before any `stat` |
| History and incidents | ~25% (10) | "used to read as absent", "profiled 2026-09-15", "the ancestor did", "since `turn_timeout` was retired" |
| Restatement of an ADR or ARCHITECTURE | ~12% (5) | the `WITHHELD_TOOL_NAMES` "kept rather than deleted" paragraph, which CLAUDE.md and ARCHITECTURE also carry |
| Stale | ~5% (2) | `openai_compat.py` line 12 and `backends/base.py` line 48 still describe retry as future work ("is M3") |

So this corrects the sentence above: history is about a quarter of the prose, not most of it.
The larger lever is that even the good rationale is long — most paragraphs would lose
nothing at half the length.

**Recommendation: yes, reduce it, by kind rather than to a target.** Expected result: prose
from about 6,600 lines to about 3,500 (ratio from 42% to roughly 28%), with every *reason*
kept. How, in order:

1. **Write the rule down first** (project CLAUDE.md or CONTRIBUTING): *a comment explains the
   code as it is now. How it got here goes to JOURNAL or CHANGELOG; why a design was chosen
   goes to an ADR, and the comment links it in one line.* It is the rule already applied to
   agent files ("state the rule, not the incident").
2. **Mind two traps before touching anything.** The docstrings of the `@mcp.tool` functions in
   `server.py` *are* the tool descriptions clients receive, and `ToolSpec` descriptions and
   `Config` field help strings are model-facing or generate `docs/CONFIGURATION.md`. Those are
   contract text, not comments: out of scope for a comment pass, and a behaviour change if
   edited.
3. **Make it provably behaviour-free.** Add a small check for the pass: the module's AST with
   docstrings stripped (`ast.dump` of each module, docstring nodes removed) must be identical
   before and after. That, plus the full suites, turns "only comments changed" from a claim
   into a measurement — and negative-test it by changing one literal.
4. **One module per branch, largest first**: `loop.py` (1,619 prose lines), then `server.py`,
   `sandbox.py`, `paths.py`, `tools.py`. Security-critical rationale in `paths.py` and
   `sandbox.py` is exactly what stops regressions there, so cut history in those two but
   trim the reasoning conservatively.
5. **Delegate the first draft.** A mechanical rewrite under a stated rule is the local model's
   strength: hand it one module, the rule, the list of ADRs, and the instruction to replace
   history with an ADR or JOURNAL pointer and halve each remaining paragraph without dropping
   a reason. Review the diff paragraph by paragraph; the AST check guards the rest.
6. **Stop it regrowing.** Extend the gate's existing date check (it already blocks dates in
   skill and agent bodies) to warn on a date inside a `src/` comment, and print the prose
   ratio per module in the gate's output as a report rather than a block.

**The size-budget headers have become changelogs again.** `docs/DISPATCH.md` opens with 73
lines of raise history, `docs/ARCHITECTURE.md` with 59, `CONTRIBUTING.md` with 50,
`docs/AGENTS.md` with 45. ARCHITECTURE's header was reset on 2026-09-08 for exactly this
reason, and has regrown. Suggest: the header holds only the number; the reason goes in the
commit, and `git log -L 1,1 <file>` is the history (the reset note already says so).

**Record volume.** In four weeks: 101 ADRs, 248 CHANGELOG entries (8,912 lines), 63 JOURNAL
entries. Many ADRs record tuning (temperature, a rate floor) rather than architecture. Two
options: raise the bar for an ADR to "changes a structural decision", or split tuning into
a separate log. As it stands, finding the ten decisions that shape the system means reading
past ninety that do not.

**Configuration descriptions carry measurement narratives.** Several `Config` field
descriptions in `docs/CONFIGURATION.md` run to 150 to 250 words of history (for example
`reply_budget_margin`, `rate_sample_seconds`). A setting's description should say what it
does and link the ADR.

## 5. Best practices: MCP, agents, skills

**MCP server — strong overall.** Six tools, differentiated descriptions of 392 to 622
characters, every argument described in `inputSchema`, an `enum` for `effort` derived from
config, a described `outputSchema`, correct `readOnlyHint` and `idempotentHint`, short
server `instructions`, a resource for the long form, errors returned as `ToolError`, stdout
kept clean and no network call at startup. That is better than most published servers.
Gaps: R1 (stdin), R2 (cancellation is not honoured — the spec says a receiver should stop
work), R7 (progress), R8 (contract drift). Minor: no `title` annotations, and the two
writing tools could state `destructiveHint`/`openWorldHint` explicitly rather than rely on
defaults.

**Agents.** R6 is the main one. Beyond that, the agent bodies are good: rules, not stories,
with clear outputs. R8 lists the stale sentences.

**Skills.** Descriptions follow the what-plus-when pattern. `docs-audit-dispatch` (266 lines)
would benefit from progressive disclosure: keep the runbook in `SKILL.md` and move the
check-class definitions and sizing evidence to a referenced file. It also contains
narrative that its own NARRATIVE class would flag ("A narrow arm returned thirteen of
sixteen...").

**Correction to the first version of this section.** It said the real workload "flattens at
about 70 tok/s from four streams up". That came from `analyse_transcripts.py concurrency`,
which spreads a turn's tokens over its whole backend interval (prefill included) and reads
all history, including turns from before the retry-accounting fix. With the clean per-attempt
rate there is no plateau. The script's `concurrency` report should be switched to
`out_tok_s` or retired, since it understates the cluster by about a third.

**The rate memory is conservative, mostly because of outliers.** Every bucket's mean sits 4 to
9% below the measured rate. Buckets 3 to 6 hold 11 samples between 1.5 and 3.5 tok/s. The
sampler's prefill guard drops a window only when it generated *zero* tokens
(`loop.py`, `RateSampler.record`), so a window in which most running requests were still
prefilling and one produced a trickle is filed as a near-zero rate for the whole width.
Four such samples move a 64-sample bucket's mean by about 6%. With `reply_budget_margin` at
0.6 on top, the effect is small but systematic: every priced ceiling is a few percent short.
**Agreed with the operator: price from the bucket median** (`RateHistory.expect`, `loop.py`
lines 676 to 725, replacing `fmean` in both places). It reads 1 to 7% below measured
instead of 4 to 9%, and it ignores the prefill-window outliers without a new threshold. The
widening rule (worst of the busier buckets) stays as it is, on medians.

**Resending reasoning is not a lever (measured twice).** In multi-turn delegations of the
last 7 days, 91% of output is in turns 2 and later, but the median later turn is only 1,191
tokens: the mass is a few heavy turns. And resent reasoning never reaches the model on this
stack anyway (R25). Visible working notes are the way to carry a plan across turns.

**Opportunities, ranked by expected gain**

- **P1 — Reasoning volume (spike, then config).** `low` is barely cheaper than `high` here
  (median 9.4k against 12.6k tokens, and a *higher* reasoning share), which supports PLAN 62
  ("effort may be binary"). The one level that is cheap is `off`: 12 times fewer tokens and
  about 9 times faster at the median. Run a quality A/B of `off` against `low` on a fixed set
  of mechanical tasks (summarise, quote, list, first-pass review). If `off` holds up, make it
  the default for those and keep `high` for reasoning work. `thinking_default` is `low` today.
  Caveat: the per-level figures are not a controlled comparison, because callers chose the
  level per task. The spike should run the *same* tasks at all three levels.
  *Operator question: the docs audit should keep reasoning on, right?* Yes. An audit compares
  a document against code and decides whether they disagree, which is judgement; `off`
  would turn it into retrieval. Suggested policy: two levels in practice. `high` for
  judgement (audits, review, design questions), `off` for transformation and retrieval
  (extract, quote, summarise, reformat, and audit pass 13, ESCAPE ABUSE, which the skill
  already calls retrieval). `low` earns a place only if the spike shows it is meaningfully
  cheaper than `high` on the same task. For audits the cost lever is P2 (cap the reasoning,
  keep it on) and narrow passes, which the dispatch skill already prescribes.
- **P2 — A reasoning budget at the server (spike).** The p90 delegation generates 39k to 57k
  tokens, which is 30 to 45 minutes at about 20 tok/s. ADR-0017 found the reasoning-budget
  parameter refused on the version then deployed. Re-check on the current vLLM build whether
  a reasoning-token budget is supported for this model; a cap of a few thousand tokens would
  cut the tail and most of the 26% no-answer waste, since those runs are mostly reasoning
  that never reached an answer.
- **P3 — Speculative decoding (spike).** With decode at 96% and most wall time at
  concurrency 1 to 2 (78k s at one stream, 36k s at two), draft-token methods give the
  largest gains exactly there. Check whether the served checkpoint ships multi-token
  prediction weights that vLLM can use as a drafter, and try n-gram prompt lookup for review
  and quoting tasks. Benchmark at concurrency 1 and 6; the gain usually shrinks as batches
  grow.
- **P4 — Topology (spike).** The endpoint reports tensor parallelism of 2 across the two
  machines, which puts a cross-machine all-reduce in every decode step. If a quantised copy
  of the model fits on one machine, two independent replicas behind one endpoint (a small
  load balancer, so this server keeps one `base_url`) could roughly double fan-out throughput
  and speed up single streams. If it does not fit, compare pipeline parallelism against
  tensor parallelism for this workload. Needs the model's memory footprint and a benchmark.
- **P5 — Context size (weak signal, benchmark it).** At concurrency 1, turns with 50k to
  100k-token prompts decoded at a median 29 tok/s against 44 for 25k to 50k (5 and 6
  samples only). If a controlled benchmark confirms it, prefetch less for tasks that do not
  need it; the prefetch budget is 140k tokens by default.
- **P6 — Stop paying for abandoned work.** R2 (cancel does not reach the cluster) costs about
  9,500 tokens per cancel in the #274 measurement. Fixing it is free throughput.
- **P7 — Width past six (benchmark before changing).** KV has never been the limit
  (operator report; 3.7% used at four running this session), and aggregate is still rising
  at six, so a seventh and eighth stream would add some throughput to wide fan-outs. The
  price is every stream slowing, which shrinks every reply ceiling. Measure 8-wide with the
  real prompt sizes before raising `max_inflight_seqs` and the endpoint's own sequence limit.
- **Not worth it now:** prefix-cache tuning (prefill is 3.4%) and the retry ladder (measured
  near zero; the old retry-accounting defect is no longer visible in the data).
